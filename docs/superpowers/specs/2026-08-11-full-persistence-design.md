# 전체 저장 기능 DB 영속화 설계

## 목표

신규 케이스, 관리대상, 알람 상태, 조치계획, 알람 규칙, 전환 규칙, 코드 관리에서 생성·수정한 값이 Neon PostgreSQL에 저장되고, 화면을 새로고침해도 동일하게 표시되도록 한다.

## 현재 원인

신규 케이스와 일부 알람 동작은 React 화면 상태만 변경한다. 마스터 관리 데이터는 DB 테이블과 API가 없어서 브라우저를 새로고침하면 초기 예시 데이터로 돌아간다. 조치계획도 저장 뒤 DB 목록을 재조회하지 않아 화면과 DB의 상태가 어긋날 수 있다.

## 설계

### 데이터 모델

- 기존 `alarms`, `targets`, `action_plans`, `action_tasks`, `audit_events`를 계속 사용한다.
- `master_rules` 테이블을 추가한다. 종류(`alarm` 또는 `conversion`), 규칙 ID, 이름, 적용 범위, 임계값, 활성 상태를 저장한다.
- `master_codes` 테이블을 추가한다. 코드값, 코드명, 분류, 활성 상태를 저장한다.
- 규칙 ID와 코드값은 각각 고유값으로 제한한다.

### API

- 알람: 목록 조회, 상세 조회에 더해 상태·검토 담당자 수정 API를 제공한다.
- 관리대상: 목록 조회, 생성, 수정 API를 제공한다. 신규 케이스 등록은 이 생성 API만 사용한다.
- 조치계획: 생성 후 연결된 관리대상을 갱신하고 최신 목록을 다시 조회한다.
- 마스터 관리: 규칙과 코드를 종류별로 목록 조회, 생성, 수정, 활성화/비활성화할 수 있는 API를 제공한다.
- 모든 쓰기 요청은 본문을 검증하고, 쓰기와 감사 이력 기록을 하나의 DB 배치로 실행한다.

### 화면 동작

- 모든 저장 버튼은 API가 성공한 뒤에만 화면 상태를 바꾼다.
- 저장 성공 후에는 해당 목록을 DB에서 다시 불러와 화면을 맞춘다.
- 저장 실패 시 임시 화면 변경을 되돌릴 필요가 없도록, API 성공 전에는 목록을 변경하지 않는다. 사용자에게 재시도 안내를 보여준다.
- 마스터 관리의 알람 규칙, 전환 규칙, 코드 관리는 각각 별도 DB 데이터로 표시한다.

### 초기 데이터와 마이그레이션

- 새 테이블과 고유 제약은 Drizzle 마이그레이션으로 추가한다.
- 현재 화면의 예시 규칙·코드를 결정적인 초기 데이터로 넣는다. 재실행해도 중복되지 않으며, 사용자가 만든 값은 덮어쓰지 않는다.
- 기존 알람·관리대상 초기 데이터와 UUID 관계는 그대로 유지한다.

### 오류 처리 및 검증

- API는 입력 오류에 400, 존재하지 않는 데이터에 404, DB 오류에 비밀정보가 없는 500 응답을 반환한다.
- 저장 API를 가짜 DB로 실행하는 테스트를 작성해, 성공·실패·새로고침용 재조회 흐름을 검증한다.
- 전체 테스트, 빌드, 마이그레이션 SQL 검사를 통과해야 완료로 판단한다.

## 완료 기준

각 화면에서 생성 또는 수정한 뒤 F5를 눌렀을 때, Neon DB에 저장된 동일한 값이 다시 표시된다. 신규 케이스 등록을 포함한 모든 저장 버튼이 화면 임시 상태만 바꾸는 경로를 남기지 않는다.
